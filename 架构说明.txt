YT-DLP 下载器 1.8.0 架构说明

一、模块划分（src\ 下平铺，pathex=[src]）
paths.py：所有位置的唯一来源（RESOURCE_ROOT、VENDOR、BIN、APP_DIR、STATE_DIR）和调用时计算的路径函数：settings_file、failed_file、log_file、engines_dir、tmp_dir、work_dir、collect_dir、cache_dir（都在 STATE_DIR 下）、default_output（APP_DIR\下载文件）、catalog_path、purge_stale、atomic_write_text。只用标准库。
procutil.py：HIDDEN、process_environment、Windows 作业对象 JobObject、terminate_tree、alive、单实例互斥量、在文件夹中显示、任务栏闪烁。applog.py：日志初始化与异常钩子。settings.py：settings.json 的类型化读取和原子保存。这三个模块只依赖 paths。
urls.py（链接提取、清理、link_key、classify、normalize）、formats.py（七种格式预设 PRESETS / MODES / format_args）、naming.py（三种命名与改名规则）：纯函数，只用标准库。
unfinished.py：failed-downloads.json（未完成列表）的读写与合并；updater.py：引擎路径与版本缓存、版本检查、下载安装、恢复内置引擎。两者都不导入 engine。
engine.py：Options、build_command、parse_line、Runner（下载队列）、diagnostics；保留 1.5.1 的全部名称供旧代码导入；顶层不导入 library。library.py（SQLite 历史、订阅、归档）、collector.py（Scrapling 采集与采集子进程）。
ui_theme.py：设计令牌、主题补丁、控件工厂、ttk 样式、DPI 调用；只导入 customtkinter 和 PIL。progress.py：平滑进度条，颜色取自 ui_theme。
studio.py：StudioApp 外壳（窗口、侧栏、共享状态、poll、handle、set_busy、关闭流程）；从 ui_download 再导出 FORMATS、bytes_text、time_text。
ui_download.py、ui_settings.py、ui_log.py、collection_ui.py、library_ui.py：页面混入类 DownloadUI、SettingsUI、LogUI、CollectionUI、LibraryUI；class StudioApp(DownloadUI, SettingsUI, LogUI, LibraryUI, CollectionUI, ctk.CTk)。混入模块在模块级不导入 studio。
app.py：命令行参数、单实例、日志、主循环；--self-test 与 --collect-worker 分支不加载 Tk、ui_theme、studio。
i18n.py 与 i18n_*.py（1.7.0）：界面语言（简体中文 / 英文），只用标准库，不导入程序的其他模块，所以任何模块（包括 library.py）都可以导入它；详见第十三节。
messages.py、i18n_legacy.py 与 i18n_legacy_data.py（1.8.0）：消息编号（Message / Raw / Value、show、存储的附加字段 msgs）和旧数据的冻结读取器；messages 在模块级只导入标准库和 i18n（i18n_legacy、i18n_maps 用到时才导入），i18n_legacy 只被 messages 导入；详见第十四节。

二、事件流
后台线程（下载 Runner、引擎更新 EngineUpdater、采集 CollectionRunner）是唯一的事件发送者：emit(kind, value) 先交给资料库记录（download_event，失败只记日志），再放入线程安全的 queue.Queue。
界面每 25 ms 调一次 poll：在 5 ms 预算内取出事件（每次最多 200 个，连续的 progress 合并为一个），交给 handle(kind, value)。handle 以 collect_ 开头的交给 handle_collection，其余按分发表 self.handlers[kind] 调用各页面的 on_<kind> 方法，未知类型忽略；单个处理函数出错只记录，不会让 poll 停下。poll 末尾刷新日志缓冲和倒计时显示。
每次开始一个活动（下载、更新、采集）都把 run_token 加一，旧活动迟到的事件被丢弃；worker / worker_operation 登记当前线程。看门狗每秒检查：线程已结束但没有收到终止事件时，补发一个合成的终止事件，窗口不会卡在忙碌状态。关闭窗口时先停止任务，8 秒后仍未结束则强制关闭。
事件载荷只做增量扩展：item 增加 key、format、origin、multi；新增 media、queued、engine_check、update_status、update_progress；item_done 和 done 增加 url、title、path、error、reason、skipped、blocked、unfinished、engine_error 等键（核心修复轮又给 item_done 加了 format，供历史按“链接 + 格式”记录跳过的条目）。1.7.0：queued 增加 items，每个移入队列的条目一项 {url, format}，选项与本次运行不同时另有 options（to_dict，不含代理和 cookies）；urls、first_index、total、overrides 不变。Library.download_event 有 items 时按条目扩展任务记录，同一链接以两种格式加入时两种都保留；界面的 on_queued 为需要补上的行取各条自己的选项。读取方对新键一律用 .get()。
外观（WP7）：ui_theme.on_appearance(callback) 登记在外观模式改变后要调用的函数（Tk 控件的绑定方法以弱引用保存，窗口销毁后自动移除；其他函数在其控件已不存在而出错时移除）；ui_theme 在 customtkinter 的 AppearanceModeTracker 上挂一个总回调 _appearance_changed：先按新模式重设各根窗口的 ttk 样式，再给所有存活的表格重新着色（条纹、表头、空表提示），最后依次调用登记的函数（例如日志页 refresh_log_colors 重设日志标签颜色）。单个回调出错只记录，不影响其他回调。只经 resolve() 取色的控件（右键菜单在每次弹出时用 resolve() 构建）自动取当前模式；SmoothProgressBar 在 _set_appearance_mode 中重设画布、轨道和填充色。

三、下载队列（Runner）
Runner(emit, library=None)。download(urls, options, overrides=None) 在一个工作线程上逐条处理；enqueue(urls, options=None, overrides=None) 可从任何线程调用：只在队列仍开放时接受，按（link key, 格式键）去掉本次运行中等待、进行中或已完成的重复链接，放入收件箱并按接受顺序返回，界面据此立即追加行（下标连续）。工作线程每条开始前取收件箱；结束时先关闭队列再取一次，所以每条被接受的链接都有 queued 事件，没跑到的记为 unstarted。
每条的顺序：被 YouTube 验证拦截的站点 -> item_done(skipped='bot_check')；开启跳过已下载且历史里有同格式记录、文件仍在 -> item_done(skipped='downloaded')；item 事件；稳健模式下的间隔等待（engine.PACE_SECONDS = (10, 20)，从 Runner.last_media_end，即上一条成功下载结束时算起，可取消，事件 waiting.kind = interval）；建命令；429 冷却循环（原样保留：300 s、600 s、上限 900 s 或 Retry-After，暂停整个队列）；字幕失败时去掉字幕重跑一次；item_done。启动 yt-dlp 失败或引擎报 no such option 时整个队列停止（engine_error），其余链接记为 unstarted。
1.7.0 重跑与 429：1.6.0 主运行的 429 尝试循环原样移到 Runner._cooled(command, index, files)，主运行、-k 重跑（_keep_source）和去掉字幕的重跑都经过它；重试计数 self._rate_attempt 每条重置、三种运行共用（最多 2 次冷却重试，然后暂停队列），停止立即结束等待。字幕请求的 429 仍不冷却（RATE_LIMIT_PATTERN 忽略 Unable to download video subtitles），直接去掉字幕重跑。_run_once、_wait 和 finally 中的未完成列表合并块在 1.7.0 中与 1.6.0 逐字节相同；1.8.0 只改了其中经批准的表达式：_run_once 读取循环里的 S1（waiting 事件的 reason）和 S2（归档信息保存失败的日志），合并块 except 里的 S3（失败清单未能保存的日志），以及 _wait 的等待日志行（改为 msg('core.engine.waiting', ...)），其余一字未动（test_protected_blocks.py 检查受保护的块，见第十四节）。带 -k 运行且开了字幕的条目，无论成功、失败还是被停止（1.7.0 修复第 2 轮：停止或失败后留下的字幕文件在重试时已属“本条开始前就有”，带 -k 的重试永远不会再删它），由 _discard_subtitles 删除本条开始前不存在、属于本链接（或其转换的旧文件、引擎报告的媒体 id）的字幕文件；重试会重新获取字幕。
1.7.0 已有文件（多条目和统一归档的条目；单个链接仍用上面的 _kept / _source 规则）：_present_media(folder, preset) 找出保存目录中已是本预设最终文件（工作名“标题 [id].最终扩展名”，不含格式分片、部分文件和链接）的文件，_present_filters 据此生成 --match-filters（id 不在其中，或 id 相同但标题不像已有文件的标题，即放行；标题比较文件标题的前 12 个字母和数字，其间允许任何非字母数字字符，包括下划线 SKELETON_GAP = [\W_]*，因为引擎在文件名中把时间的冒号写成 _（10:30 -> 10_30）；非字母数字字符一律写成 \uXXXX；标题比较以 (?i) 开头、不分大小写，与 Windows 文件名一致（_title_test，1.7.0 修复第 2 轮）。原始最佳（--audio-format best）的已有文件中，扩展名也是其他预设固定转换结果的（BEST_SHARED_EXTENSIONS：.mp3、.flac、.wav、.m4a），_present_media 通过 shared 参数单独列出，_present_filters 为它们加一条按所选格式放行的过滤（_format_test：.mp3/.flac/.wav 要求 ext 不是该扩展名；有 .m4a 时只放行从不含 AAC 的格式 _BEST_NO_AAC）；引擎在选好格式之后、下载和写入任何文件之前检查 ext，因此 MP3 预设的文件不再挡住原始最佳下载原始音频，而原始最佳自己会得到的同名文件仍被跳过），_skip_present 把它们放在 -- 之前（去掉字幕的重跑同样带上）。引擎因此在下载之前就跳过这些条目，不会重写已有文件的标签、封面或字幕。放不下 COMMAND_LINE_LIMIT 时（几百个已有文件），_filter_config 把同样的过滤条件写进 STATE\tmp\run-<pid>-<随机> 下的 filters.conf（每行一个 shlex 引号包起的选项，纯 ASCII），命令行只加 --config-locations <文件>（--ignore-config 仍读取它）；本条结束后 _drop_filter_config 删除这个文件夹，进程被结束时由 paths.purge_stale 清理。只有这个文件无法写入（或其路径会被引擎展开 ~、%NAME%、$NAME）时，本条才改为不写标签、封面和字幕，并记一行日志。probe_args() 也带上 --match-filters、--config-locations -（读空的标准输入）和 -k，新引擎的参数试运行因此覆盖这些参数。_intercept 把引擎的跳过行换成中文；_present_done 把跳过的文件重新登记到归档（Archive.media），已归档的单个链接没有新文件时像 _kept 一样报告原文件。跳过的条目不再作为新任务的文件（不发 media / file 事件）。
_run_once 的读取循环（睡眠/限流状态机）在 1.7.0 中与 1.5.1 逐字节相同（1.8.0 只把循环里的两处中文表达式 S1、S2 换成了消息编号，状态机不变，见第十四节），只在子进程环境、作业对象、两处钩子和 finally 中增加了内容；核心修复轮在循环之外加了三行（第一句 command, sealed = self._seal_command(command)，以及 job.assign 之后的两行，见下面的“封印标记”）。
封印标记（核心修复轮）：引擎的私有输出行（__GUI_MEDIA__、__GUI_FILE__、__GUI_TITLE__ 等，由 --print / --progress-template 产生）只认引擎自己打印的。每个 Runner 有一个随机封印（'__GUI' + 16 位十六进制 + '_'），_seal_command 只把它写进这些参数（不碰 -- 之后的链接），_EngineOutput 包装子进程的二进制 stdout：按与通用换行模式相同的规则切行，把带封印的行还原成 parse_line 认识的普通标记，给以普通（未封印）标记开头的行前面加一个空格（成为普通日志行）；一个物理行内裸 CR 之后的片段如果像“has already been downloaded”行，也加空格。所以网站返回的任何文字（含 CR、LF）都不能伪造标记行或“已下载”行。没有 --print 的脚本子进程不封印。
_intercept 的其他规则（核心修复轮）：可能复述 cookies 文件某一行的引擎输出（cookie file entry、带引号内容的 cookies file 报错，以及使用 cookies 时含四个以上制表符的行）替换为 COOKIE_LINE_SKIPPED / COOKIE_LINE_FAILED，_note_line 在保存 last_error 前用同一规则，所以日志、未完成列表和历史都不含 cookies 内容；check_cookie_file 要求 yt-dlp 保留的第一行是 “# Netscape HTTP Cookie File”（或 “# HTTP Cookie File”），并返回绝对路径。单个链接、无归档时，“<路径> has already been downloaded”而该路径在本条开始前就已在保存目录（self._existing）：是本条格式的最终文件（_is_final_file）则立即结束引擎（_kept，文件不被重写标签或封面），记为完成；是这个链接的另一种格式（转换的源文件）则结束引擎（_source），download() 在受保护的 429 循环之后带 -k（_keeping_source）再跑一次，原文件保留。最终修复第 1 轮：引擎读到这一行后往往立刻转换并删除源文件，来不及结束引擎；所以 download() 在本条开始前就用 _other_formats 查看保存目录（工作文件名“标题 [id].扩展名”、id 规则同 _old_partials、不是本格式的扩展名、视频格式只看视频文件），有这样的文件就从一开始带 -k（_keep_early），引擎读到这一行时不再结束、只记日志；结束后再跑一次只留给 id 猜不中的情况。带 -k 而引擎实际重新下载了（标题变了或 id 只是相似）时，_discard_kept 删除 -k 留下的新下载源文件和格式分片（本条开始前不存在、带本链接 id、不是本条报告的文件），与不带 -k 时引擎自己删除的一样。格式分片（.f<格式>.<扩展名>）交给引擎自己合并。
Runner.download 的其他规则（核心修复轮）：停止发生在文件已交付之后（单个链接，item.path 或本条最后一个 file 事件的文件在磁盘上）时，本条报告为完成（item_done success=True），不进未完成列表，队列仍然停止；保存目录里有本链接 1.5.1 留下的部分文件（_old_partials：* [<id>].*.part、.ytdl、.part-FragN）时，本条不用 -P temp:，由引擎在原处续传；temp_path 只在工作文件夹可建、可写时返回它（_usable_work），建立失败时整条不带 -P temp:。ERROR_REASONS 在网络规则之前识别“Unable to download <非视频数据>: HTTP Error 403/404/410” -> 页面不存在或无权访问（4xx），最后兜底 HTTP Error 410 -> 链接已失效（410）。归档包装为 _SafeArchive，sqlite3.Error 变成 OSError('资料库无法写入：…')，由受保护循环原有的 except 记录为归档错误，队列继续。Runner.cancel() 在引擎已退出时额外结束作业对象（引擎留下的子进程仍占着输出管道时，停止才能结束等待）。
封面与命令行长度（最终修复轮）：用工作文件夹时 build_command 另加 -P thumbnail:<工作文件夹>，封面图片的最终位置也在那里，引擎不会把保存目录里主人自己的“<工作名>.jpg”当作封面嵌入后删掉；不用工作文件夹（-P temp: 不加）而嵌入封面时，_owner_pictures 在本条开始前的保存目录列表中找与本链接 [id] 对应（多文件链接或猜不出 id 时为任何带工作名）的图片，找到就本条不嵌入封面（embed_cover=False）并记一行日志，图片不动。_intercept 记下引擎“[info] Writing video/playlist thumbnail … to: <路径>”行写在保存目录或工作文件夹里的封面（_covers、_cover_folders，裸 CR 之后的同样行加空格不算数），本条结束时 _discard_covers 删除其中仍在、且本条开始前不存在（self._existing）的图片及其转换后的同名图片。build_command 在完整命令行（subprocess.list2cmdline）超过 COMMAND_LINE_LIMIT = 32000 个字符时抛出 engine.LinkTooLong（ValueError 的子类，“链接过长…”）：Runner 中由“此链接无法开始”的既有处理记为这一条失败，队列继续，不再被当成引擎启动失败（WinError 206）而停掉整个队列；界面开始任务前的检查（ui_download.read_form 和 launch，每组选项和来源页只用一条链接检查一次）跳过过长的链接、改用同组的下一条链接检查，过长的链接照样进入任务，由 Runner 单独记为失败；只有全部链接都过长时才弹出“检查输入”，任务不开始。“无法启动下载引擎”日志行去掉 Windows 错误文字自带的句号（_sentence）。
命令行顺序与参数见 SPEC §3.4；所有参数都在内置 yt-dlp 2026.10.21 中存在。yt-dlp 总是先以“标题 [ID].ext”写入，after_move 后由 Runner 按命名方式用 os.rename 改名（不覆盖，冲突加“ (2)”）；整个播放列表或统一归档时不改名、不用 -P temp:。

四、未完成列表（%LOCALAPPDATA%\YtDlpDesktop\failed-downloads.json）
格式：{"version": 1, "urls": [...], "options": {...}, "entries": [{"key", "format", "url", "title", "reason", "error", "time", "referer", "options"}]}。
entries 是权威数据；urls / options 是给 1.5.1 看的旧视图（最新一组 options 相同且为 1.5.1 已知格式的记录，否则为空）。format 是格式键（音频为预设 id，视频带画质时为 id@画质），reason 为 failed / stopped / unstarted / blocked，options 为 Options.to_dict() 去掉 referers 与 archive_contexts。没有 entries 键的旧文件按旧 URL 迁移；读不了的文件当作空列表。
合并规则（每次运行结束，unfinished.merge）：1. 删除与本次已完成或“已下载过”条目同格式、且 key 等于其链接键或媒体键（<extractor_key 小写>:<id>，generic 除外）的记录；2. 本次失败、停止、未开始、暂缓的条目按（key, format）插入或更新；3. 其余保留。列表为空时删除文件；写入用临时文件 + fsync + os.replace。
重试使用记录自己的 options，代理、cookies、稳健模式取当前设置。engine.store_failed_job / load_failed_job 作为兼容包装保留。
读取与保护（核心修复轮）：_read(path) 是唯一的读取函数，返回（条目，问题，文件标识）；文件大于 MAX_SIZE（5 MiB，两个版本的读取上限）、读不了、截断、不是 JSON、版本或结构不对、有被丢弃的条目、或 1.5.1 旧格式无法迁移时，“问题”是一句中文原因。读到 PermissionError 时 _read_text 在 READ_RETRY（1 秒）内重试，别的程序短暂占用不会被当成坏文件。load() 照旧不改任何东西、读不了时返回空列表。Runner.download 的 finally 中受保护的合并块在核心修复轮唯一被批准的改动是读取调用：unfinished.merge(unfinished.load_for_merge(lambda text: self.emit('log', text)), results)；1.8.0 另有一处批准的改动 S3：其 except 中的日志改为 msg('core.engine.unfinished_not_saved', error=message_of(error))（见第十四节）。load_for_merge 遇到有问题的文件时先把它改名保留为 failed-downloads.bad-<YYYYmmdd-HHMMSS>[-n].json（取一个空闲名字，os.rename，从不覆盖），在 download.log（记录器 YtDlpDesktop.unfinished）和任务日志各写一句说明，再返回可用的条目；改名失败时抛 OSError，调用方原有的 except 不写任何东西。save() 有同样的保护（_guard）：从不覆盖或删除一个它读不了的文件（清除未完成、移除单条、store_failed_job 也都经过它）；load_for_merge 刚完整读过同一文件（路径、大小、mtime_ns 相同）时不再重读。
紧凑列表（核心修复轮）：文件写成紧凑 JSON（separators=(',', ':')，UTF-8 无 BOM）；每条记录的 options 只写与 OPTION_DEFAULTS（engine.Options 的默认值，类型和值都相同才算）不同的键，output 和 mode 总是写（ALWAYS_WRITTEN）；_clean 读取时补回默认值（_full_options），所以 load()、newest_group、legacy_view 和界面看到的都是完整 options，旧的 1.6.0 文件读出来一样。给 1.5.1 看的顶层 urls / options 照旧完整写出。编码后超过 SAFE_SIZE（4 MiB）时，最早的条目（按 time，再按列表顺序）先写入 failed-downloads.overflow-<时间>[-n].json（同一格式，临时文件 + fsync + 改名到空闲名字），然后才用较短的列表替换主文件，日志说明移走了几条；load_for_merge 得到的日志回调按线程保存，同一次合并的 save 也用它。

五、下载历史（data\library.sqlite3，增量扩展）
新增表 downloads(key, format, url, title, path, finished, job, PRIMARY KEY(key, format))：media 事件记录实际文件，非多媒体条目同时记录链接键，供“跳过已下载过的内容”查询（find_download 返回最新一行和文件是否仍存在）。jobs.data 中新增 overrides、errors（最近 20 条错误）等键；history(limit=HISTORY_PAGE, search='') 与 history_count(search='')（1.7.0：HISTORY_PAGE = 300 条一页，资料管理的“加载更多”；search 在数据库中按标题或任务的任一链接查找，json_each 读取 options.urls，LIKE 转义 % 和 _）；读-改-写操作使用 BEGIN IMMEDIATE。1.5.1 能继续读取这个数据库。
资料库被其他程序占用（1.7.0）：工作线程、采集子进程和其他调用方的忙等待仍是 WORKER_TIMEOUT = 20 秒。窗口线程（set_ui_thread，由 LibraryUI.init_library 登记）上的公开方法（UI_RETRIED，类定义之后统一包装，方法体不变；新增打开数据库的公开方法也要加入这个列表）以忙等待 0 运行，遇到锁时整次调用重复最多 UI_WAIT = 0.12 秒，然后抛出 database is locked；之后 UI_QUIET = 2 秒内该线程只试一次；直接在窗口线程用 db() / tx() 时为 UI_DIRECT_TIMEOUT = 0.05 秒。忙结果本来就会被平静处理的调用用 library.ui_wait(秒) 缩短重复时间：HistoryWriter.run 在窗口线程上的立即写入用 library_ui.UI_WRITE_WAIT = 0.03 秒（一次尝试，本程序自己的短事务碰撞时再试一次），采集结束（collect_done）读取采集记录只试一次（ui_wait(0)）。Runner 在工作线程上的“已下载过”检查（find_download）用 library.worker_wait(FIND_TIMEOUT = 2 秒)，被锁时记“下载记录无法读取，照常下载”后开始下载，不再等 20 秒。历史列表中不是 JSON 对象的记录（本程序不会写出）按标题列出、data 为空，不写入，加载更多和搜索不会因此中断。library_ui.HistoryWriter 按顺序在一个后台线程上（工作线程的超时）写入不能丢的记录：新下载任务的记录（history_create 先返回 PendingJob，写入后才有 id）、“加入队列”的链接、续接的其他格式、等待中任务的事件、合成的结束、新订阅、归档索引、采集后的订阅记录；每秒重试，直到写入或窗口关闭（关闭时日志列出没写入的内容）。被锁时下载页和资料管理页显示“资料库正被其他程序占用，稍后自动重试”，library_watch 每 2 秒重读，恢复后提示条消失并记“资料库已恢复，暂存的 N 条记录已写入。”；读取保持原有显示，需要读取记录的按钮提示稍后再点；手动开始采集在能写入记录后自动开始（最多等 COLLECT_WAIT = 120 秒）。
历史记录中的格式与多种格式（核心修复轮）：下载任务的 options['mode'] 只存 1.5.1 认识的格式，真实格式存在增量键 options['mode_v2']（stored_options()，用于 create_job 和 change_job(options=…)）；read_options() 在 job() 和 history() 中把真实格式放回 mode 并去掉 mode_v2，所以 1.6.0 的调用方看不出差别。映射：音频 · M4A 原生 -> 音频 · 原始最佳，视频 · MP4 兼容 -> 视频 · 最佳画质 MKV（library._legacy_mode）；旧格式和采集任务按原样保存。于是 1.5.1 续接这类任务时用最接近的旧格式，而不是出错。Library._extend（extend_job 和 queued 事件）按（链接, 格式）各保留一组 options：新链接进 urls（及 overrides）；任务已有的链接以另一种格式加入时，写进增量列表 options['variants'] = [{url, format, options}]，不改第一次下载的 options；同一链接同一格式照旧更新。完成情况同样按（链接, 格式）记在增量键 data['completed_variants'] = [[url, format], …]，data['completed']（链接，1.5.1 读取）不变；“已下载过”而跳过的 item_done 用其 format 键。library.job_downloads(data) 列出一个任务代表的全部下载 [{url, format, options, done}]（没有 completed_variants 记录的旧任务退回 completed）。资料管理的“继续未完成”（library_ui.resume_history，润色轮）按 job_downloads 续接：resume_plan 取每条链接的第一个未完成下载立即 launch（resume_launch：任务 options 加上与之不同的 overrides），同一链接的其他格式先用 Library.extend_job 写进新任务的记录，再由 _resume_later_step（每 RESUME_POLL = 100 ms 检查）在新运行的队列开放时经 Runner.enqueue 加入并用 append_rows 显示；运行被停止时不再交出（留给下一次“继续未完成”），运行先结束（未停止）时作为下一个任务开始。download_event 在 item_done 带错误和 reason 时另存增量键 data['last_reason'] = {error, reason}（1.5.1 忽略），历史说明行显示该原因，旧记录退回 explain_error。历史列表只在显示时变化：没有任何成功的 'partial' 下载任务显示“未完成”（history_status），从未取得标题、标题仍是“<n> 条 · <格式>”占位的下载任务显示第一条链接（history_title）；存储的状态和标题不变。

六、路径与覆盖
RESOURCE_ROOT = sys._MEIPASS（打包后为 <exe 目录>\_internal），源码运行时为源码根目录；VENDOR、BIN 在其下。APP_DIR = 环境变量 YTDLP_DESKTOP_APP_DIR，否则打包后为 exe 所在目录、源码运行时为源码根目录；STATE_DIR = YTDLP_DESKTOP_STATE，否则 %LOCALAPPDATA%\YtDlpDesktop。空值视为未设置，结果总是绝对路径。代码在调用时读取 paths.X，不在导入时复制。
catalog_path()：APP_DIR\data\library.sqlite3 存在且可写时用它，否则 STATE_DIR\library.sqlite3（资料管理页会提示）。工作文件夹 STATE\work，与保存目录不在同一盘时改用 APP_DIR\data\work（同盘、非链接、可写时）。
程序自己建立的 tmp、work、collect、engines 文件夹带标记文件 .ytdlp-desktop；purge_stale（启动时后台运行）只清理带标记或位于默认 YtDlpDesktop 目录下的内容，只删除已结束进程的 run-<pid>-* 文件夹、过期工作文件和已结束进程留下的保存临时文件（STATE 中的 settings.json.<pid>.tmp、failed-downloads.json.<pid>.tmp 和 .<pid>.overflow.tmp，STATE_TEMP；engines 中的 yt-dlp.json.<pid>.tmp，ENGINE_TEMP，由 purge_engine_downloads 清理）。两个工作文件夹用同一条年龄规则 paths.clean_work（最终修复轮统一）：WORK_STRAYS（*.temp、*.temp.*、*.tmp 和 jpg / jpeg / webp / png 封面图片）超过 WORK_STRAY_AGE = 24 小时删除，其他普通文件（可续传的 *.part、*.ytdl、*.part-FragN，合并前已完成的格式分片“标题 [id].f137.mp4”，提取音频前的原文件等）超过 WORK_MAX_AGE = 7 天删除。核心修复轮：paths.is_link(path)（lstat；符号链接或任何重解析点；无法 lstat 的条目也算链接）使 purge_stale、purge_engine_downloads 和 updater.cleanup 在每一层跳过链接与联接（本身是链接的状态文件夹、链接的 tmp / collect / work / engines 文件夹、其中的链接条目）。engine.clean_app_work 清理 APP_DIR\data\work，也调用 paths.clean_work（规则同上），不递归、不删标记文件、不经过链接，只在带标记的文件夹中进行。
settings.json（settings.py）：内容不是 UTF-8 JSON 对象时改名保留为 settings.bad.json，这个名字已存在时用空闲的 settings.bad-<YYYYmmdd-HHMMSS>[-n].json（os.rename，从不覆盖较早保存的坏文件），然后用默认值。文件存在但打不开（被别的程序以不共享方式占用；读取在 READ_RETRY = 1 秒内重试）时，load() 返回默认值并带上 '_held' 键（载入时的值和本次改过的键）：save() 不会用这些默认值覆盖原文件，而是重新读取原文件，只把本次改过的键写进去；仍读不了时不写，返回 False 并记日志。StudioApp 启动时发现 '_held' 会在任务日志写一行“设置文件暂时无法读取（可能被其他程序占用），本次先用默认设置；原文件不会被覆盖。”。
单实例：互斥量 Local\YtDlpDesktop.Instance（测试用 YTDLP_DESKTOP_INSTANCE 改名）；第二次启动把已有窗口调到前面后退出。--smoke-url 启动跳过单实例检查。

七、子进程、作业对象与临时目录
每次 yt-dlp 运行都有私有 TEMP（STATE\tmp\run-<pid>-<8 位十六进制>），结束后删除；子进程放进 Runner 的 Windows 作业对象（关闭即结束整棵进程树），停止时先结束作业对象，再用 taskkill /T /F 兜底。子进程环境：PYTHONUTF8=1、PYTHONIOENCODING=utf-8、PYINSTALLER_RESET_ENVIRONMENT=1、PATH 以 BIN 开头。
采集子进程就是本程序自身（app.py --collect-worker JOB，打包后直接启动 exe），环境用 process_environment(reset=False)，TEMP 指向 STATE\collect\run-<pid>-*，通过临时 JSON 任务文件和 JSONL 事件文件通讯（兼容 windowed 模式下 stdio 为 None）；采集停止时作业对象结束 worker 及其 Chrome，结束后删除 run-* 文件夹。

八、引擎更新（updater.py）
engine_path()：STATE\engines 中有校验记录的更新版优先，否则内置 _internal\vendor\yt-dlp.exe；engine_version() 按文件大小和修改时间缓存。check_latest() 只访问 api.github.com 的 releases/latest。EngineUpdater.run()：下载官方发布资产（只接受官方地址前缀）到每次唯一的临时文件，核对大小和 SHA256，再用 engine.probe_args()（全部格式预设和全部可选参数块）试运行新引擎，输出中出现 no such option 即拒绝；取消在最后的 os.replace 之前都有效；写校验记录失败时退回内置引擎。试运行有超时，超时结束整棵进程树。
1.7.0：参数试运行之前，_check_start 要求新引擎以 --ignore-config --version 退出码 0 结束、第一行是版本号（VERSION_LINE），否则拒绝（MSG_START“新版引擎无法正常运行（原因），已保留现有引擎。”，原因为退出码、没有给出版本号、60 秒内没有结束或无法启动）。_install 每次尝试 os.replace 之前都检查取消。restore_bundled() 删除校验记录和更新的 exe（清除只读属性；两者删掉其一即可，因为没有校验记录的 exe 不会被使用；只有两者都删不掉、且是被其他程序暂时占用（共享冲突）时才重试，合计最多 RESTORE_RETRY = 1 秒；正在运行的 exe（拒绝访问，WinError 5）不重试，所以下载正在用已更新的引擎时恢复不会让窗口停顿），只有之后 engine_path() 是内置引擎时才返回 True，否则抛出 UpdateError(MSG_RESTORE)；偏好设置的 restore_engine 这时只显示“恢复未完成”并刷新版本标签，不显示“已改用内置引擎。”，也不写“已恢复内置引擎”日志。
每天最多一次的版本检查（偏好设置可关）是程序唯一的后台网络请求，从不自动安装。

十一、构建、发布检查与安装
第三方程序：vendor.lock.json（随源码提交）固定 yt-dlp、Deno、FFmpeg 的仓库、发布标签、文件名、下载地址和 SHA256（FFmpeg 用 yt-dlp/FFmpeg-Builds 的月末构建，该仓库长期保留月末构建、约两周后删除每日构建），以及 yt-dlp 与 Deno 同一标签下的许可证文件和 SHA256。prepare_vendor.py 默认按锁下载到 build\vendor-cache（vendor\ 中不留 *.zip / *.part），逐个核对 SHA256（不符即停止，vendor\ 不变），在缓存中组装后整体替换 vendor\bin、yt-dlp.exe 和三个程序的许可证（vendor\licenses\python-packages 缺少时从 .venv 已安装的包复制），最后写 vendor\manifest.json。--update 查询最新的 yt-dlp、Deno 和最新一个已结束月份的 FFmpeg 月末构建，只改写锁，不改动 vendor\（检查新锁后再运行 prepare_vendor.py 按新锁准备）。--record-local 不联网：核对 vendor\yt-dlp.exe 仍是清单所记的文件，把 yt-dlp.exe 与 vendor\bin 各文件的 SHA256 记入清单（deno.exe 归 Deno，ffmpeg.exe、ffprobe.exe 和 DLL 归 FFmpeg，其他文件拒绝；同一个 FFmpeg 库有两个大版本号的 DLL，例如 avcodec-62.dll 与 avcodec-64.dll，也拒绝，因为多出的是旧版 FFmpeg 的残留），删除 vendor\ 中的下载残留；用于旧版 prepare_vendor.py 准备的 vendor\。vendor\manifest.json 仍是列表、yt-dlp 在第一项（updater 读取第 0 项的版本），每项有 repository、version、tag、asset、sha256、url、source 和 files（vendor\ 内路径 → SHA256），FFmpeg 另有 display_version（设置页显示）和 build。
python -B build.py [--skip-tests]（用 .venv 的 Python）：1. 按 vendor\manifest.json 核对 vendor（yt-dlp.exe 的 SHA256；vendor\bin 必须恰好是清单列出的文件且 SHA256 一致，ffmpeg.exe、ffprobe.exe、deno.exe 必须在清单中，不写死 FFmpeg 的 DLL 名称；清单没有文件列表时拒绝并提示 prepare_vendor.py --record-local；vendor\ 中有 *.zip / *.part 下载残留时拒绝（app.spec 本来也不打包它们）；与 vendor.lock.json 不一致只提示）；2. run_tests.py --all；3. PyInstaller app.spec（文件夹版：EXE exclude_binaries + contents_directory='_internal'，vendor 作为 Tree 只加入一次，PIL.ImageDraw / ImageFont 作为隐藏导入）输出到 build\dist；4. 复制为 build\package-<APP_VERSION>\YT-DLP下载器（1.8.0 为 build\package-1.8.0），写 build.json（构建前的 source_sha256、exe_sha256、时间）；5. run_tests.py --all --exe <暂存 exe>，再运行 verification\verify_release.py。全部输出都在 build\ 下，从不下载。
verify_release.py（1.7.0 起版本号取自 src\engine.py 的 APP_VERSION，与 build.py 相同；界面冒烟接受“YT-DLP 下载器”和“YT-DLP Downloader”两种窗口标题）依次检查：文件布局（_internal 顶层无 av*/sw* DLL、_internal\vendor\bin 恰好是打包的 manifest.json 列出的文件且 SHA256 一致、yt-dlp 哈希、许可、node.exe、FreeType），随后在程序第一次运行之前列出暂存目录的每个文件（相对路径、大小、SHA256）；两次 --self-test（只重定向 LOCALAPPDATA 时 app_dir 必须是暂存目录）；夹具下载自检（含归档）；界面冒烟（10 秒内出现窗口，WM_CLOSE 后退出码 0，日志中无图标绘制失败和错误）；report.json 和 build.json 必须属于当前源码和当前 exe（-k 的部分运行、旧源码或旧 exe 都不通过）；最后暂存目录必须与开头的文件列表逐个一致。通过后写 build\verify\release-<APP_VERSION>.json（file_list：文件数、总大小、列表本身的 SHA256 和全部文件），失败时不留下该文件。
install_release.py --stage <暂存目录> --target <程序目录> [--dry-run] [--shortcut] [--rollback] [--old-version V] [--instance-name NAME]：程序在运行时拒绝（互斥量存在，或 exe 无法以写方式打开）；要求 release-<版本>.json 与暂存 exe 一致，并按其中的 file_list 逐个核对暂存目录（列表须与它自己的 SHA256、文件数和总大小相符；发布检查之后改过（包括大小不变的改动）、多出或缺少任何文件都拒绝，没有 file_list 的旧记录也拒绝，此时尚未移动或复制任何东西，--dry-run 同样核对）；先复制为 _internal.new 和 YT-DLP下载器.new.exe，核对文件数与大小后再按 file_list 逐个核对副本，不符即删除副本并拒绝；之后的全部改动都是改名，事先列在程序目录的 install-journal.json 中，每完成一步记录一次：旧程序按布局移开（单文件改名为 YT-DLP下载器-<版本>备份.exe，记录中保存它的 SHA256；文件夹版连同安装记录移入 _previous，更早的 _previous 先改名为 _previous.old-<时间>，提交后才删除；移入 _previous 的那份记录若指向被删除的更早版本，就改为接到它的前一个程序上，使回滚链始终是“本次 → 上一次 → 1.5.1”；无法保留的记录改名为 install-receipt.superseded-<时间>.json，从不覆盖）；启用新程序，最后把事先写好的 install-receipt.pending.json 改名为 install-receipt.json（提交点）；从安装位置运行自检、下载自检和界面冒烟，通过后把安装记录改写为 "checked": true（mark_checked）。从提交点到这次改写之间，新程序已经启用但还没有检查过：这段时间里的任何失败或 Ctrl+C（也包括提交后的清理，即删除更早的 _previous 时）都由 abort_install 自动回滚（自检失败退出码 2，Ctrl+C 退出码 130，回滚也失败时 3 并说明当前状态和命令）。改名序列、提交后的清理和自动回滚期间，Ctrl+C 由 HeldInterrupt 暂存（SIGINT 处理函数只做记号）：改名一定做完，之后再按这次中断处理，所以不会出现“提交了却报告为已中断”的情况；用户的 --rollback 同样在改名和清理期间暂存 Ctrl+C，提交后的回滚总是报告为已完成。进程在这段时间里被强制结束（例如直接关闭命令窗口）时，安装记录保留 "checked": false：下一次安装先把这个未经检查的安装回滚（unchecked_install），再重新安装并自检；--rollback 和 --dry-run 会说明当前程序没有完成自检。没有 checked 键的记录（较早写的，或保存在 _previous 中、当时已通过自检的）视为已检查；checked 不是布尔值的记录无效（receipt_problem）。回滚只依据 install-receipt.json，记录中的名字必须与安装脚本写入的完全一致（单文件备份还要核对 SHA256），否则不做任何更改：当前 exe 与 _internal 一起移入 _rolledback-<版本>，按记录恢复旧程序，记录改名为 install-receipt.rolledback.json，_previous 中保存的记录恢复为当前记录，因此每次回滚退回一次安装。给主人看的说明（文件夹版安装后的收尾说明、没有安装记录和记录中的文件不存在时的拒绝说明）提到的旧版备份名由 backups_to_name 决定：安装记录（或 _previous 中保存的记录）所指的单文件备份存在时用它，否则列出程序目录中实际存在的 YT-DLP下载器-<版本>备份.exe，一个也没有时不提，从不假定名字是 1.5.1。任何一步失败都按日志倒序撤销；进程被强制结束或断电时日志留在程序目录，下次运行安装或回滚时先撤销那次未完成的操作（全部改名都已完成时只补做清理），日志中只允许出现脚本自己管理的名字。data、下载文件、源码等其他内容从不触碰。exe 的完整路径不变，因此快捷方式、data\library.sqlite3、下载文件和 %LOCALAPPDATA%\YtDlpDesktop 都无需迁移。

十四、消息编号与旧数据读取（1.8.0，设计见 docs\1.8.0\spec\MESSAGES.md）
消息：src\messages.py 只用标准库，模块级只导入 i18n（读取旧数据时再导入 i18n_legacy，检查枚举值时导入 i18n_maps）。核心的每句话是 msg(key, **params) 得到的 Message：一个 str 子类，字符串值逐字节就是 1.7.0 的中文原文，另带 key、params 和来源（live / stored / legacy / foreign）；Raw 标明确定不是程序文字的内容（媒体、网页和链接的标题、主机名、用户输入的名称、yt-dlp 的 ERROR 原文），Value 是嵌在消息里的存储枚举值（格式 mode）；普通 str 表示来源未知。str(m)、f'{m}' 和异常的 str() 返回对象本身，所以键不会在传递中丢失；json、sqlite、Tk 和日志写出的都是中文原文，事件载荷的键不变（H5），黄金记录逐字节不变。cut、masked、stripped、clauses、message_of 生成保留类型和键的派生文字。
显示边界：界面只通过 messages.show(value) 和 messages.error_text(error) 显示核心或存储的值：中文下返回值本身（与 1.7.0 相同），英文下按键查英文目录、参数先各自 show；Raw 和普通文字原样显示（只把“[代理]”换成英文）。i18n.t() 的参数总是已经显示好的文字。界面自己的文字仍用 t() / label()。比较仍是值比较（engine.NETWORK_REASON 等）。
存储边界：只有 library.py 和 unfinished.py 调用 messages.decode / decode_columns / encode。encode 在每个写入的 JSON 对象里按“存储的文字本身 → {k, p}”建附加键 msgs（Raw 只在旧读取器会把它误认成程序文字时记 null，单条最多 2 KB，每次写入重建）；decode 读回时：有效条目还原成 stored 消息，后来版本写的、1.8.0 不认识但格式正确的条目作为 foreign 原样保留并在下次写入时原样写回（只对 MESSAGES.md 第 4.3 节列出的文字字段；1.8.0 不当作文字字段的字段，其条目在下次读改写时去掉，字段本身保留），没有条目的文字交给冻结读取器。读改写路径从不改动 options、checkpoint、result 和未知键。
旧数据读取：src\i18n_legacy.py 是 1.7.0 文字匹配器的冻结版，只被 messages 导入；它的数据 src\i18n_legacy_data.py 由 verification\i18n_tool.py legacy 从 verification\release-sources\1.7.0 生成（1.7.0 的模板、1.5.1 的十种无空格采集错误等变体、数字与递归规则、cookies 行片段），以后不再为新文字扩充。lift 按字段类型（error、reason、clauses、job_title、title、name）识别 1.5.1 / 1.6.0 / 1.7.0 存下的无键文字（整句、模板、200 / 900 / 70 字截断、原因与错误配对、“；”分句、任务标题与订阅名称的上下文规则）；识别出的是 legacy 消息，只用于显示，从不写进 msgs。i18n_legacy.recognise 只给测试中的哨兵用。

引擎更新（1.3.0）
空闲时在“偏好设置”中点击“检查更新”。
程序查询 yt-dlp 官方 GitHub 稳定版，下载并核对大小和官方 SHA256 摘要。（1.6.0 增加兼容性试运行，见第八节。）

批量下载（1.3.0）
支持多行链接、TXT 导入、去重和逐条任务状态。
下载队列顺序执行，单条失败会继续下一条。
Options.batch_safe 默认开启，使用 yt-dlp 原生 sleep-interval / max-sleep-interval / sleep-requests，使独立链接和播放列表条目都能遵守等待间隔。（已过时：1.6.0 中独立链接之间的间隔由 Runner 在两条之间等待，只下载一条时不等待；sleep-interval 只用于整个播放列表；sleep-requests 不变。）
HTTP、分片、解析和文件访问错误分别配置 retry-sleep；429 由调度器停止当前进程并执行有上限的队列冷却与同链接重试。
冷却通过 threading.Event.wait 实现；原生等待日志由后台读取线程解析成 waiting / resuming 事件，UI 根据单调时钟显示倒计时。
failed-downloads.json 使用临时文件替换保存未完成链接和输出设置；不保存代理凭据。UI 的“重试失败”复用该清单并恢复格式、画质、保存目录与稳健模式。（已过时：1.6.0 按条目保存，见第四节；按钮为“重试未完成”，不改动表单。）
播放列表开关关闭时仅处理单条；开启时处理整个列表。
后台事件通过线程安全队列传给界面，下载过程不阻塞窗口。
