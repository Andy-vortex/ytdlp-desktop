# WP7 - Dark palette and appearance setting (stretch)

Read: SPEC.md §3.2 (`appearance`), §3.13; handoff WP3, WP4, WP5, WP6; audit visual-12 (skeptic notes); WP3.md token table.
This package is optional. It starts only after WP6 is accepted, has its own acceptance check, and can be dropped without touching WP0-WP6: until it lands the app is light-only (nothing sets `arguments.appearance`, so `StudioApp.__init__` uses `light`, WP4 §A) and the `appearance` key is simply unused. If any acceptance item cannot be met, revert this WP's changes completely rather than shipping a half-dark UI.

Owns (edits only for appearance): `src/ui_theme.py`, `src/progress.py`, `src/ui_settings.py`, `src/ui_log.py`, `src/app.py`, `verification/snapshot_ui.py`, `verification/test_theme.py`. If the version must be distinguishable, do not bump `APP_VERSION`; the feature ships inside 1.6.0 or not at all.
Must not edit: page layouts, engine-side modules, strings other than the new setting row.

## Steps
1. Palette. For every pair in `ui_theme.TEXT_PAIRS` compute the dark contrast; adjust dark values (never light values) until each is >= 4.5:1 (FAINT and disabled pairs exempt). Starting values are in WP3.md; already measured: INK/SURFACE 13.4, MUTED/SURFACE 6.6, MUTED/BG 7.5, MUTED/SURFACE_ALT 6.0, ACCENT_TEXT/ACCENT_SOFT 5.9, WHITE/ACCENT 4.52, OK/OK_SOFT 7.1, WARN/WARN_SOFT 7.1, DANGER/DANGER_SOFT 7.0, MUTED/IDLE_SOFT 5.4. Still to measure and fix: WHITE/ACCENT_HOVER, ACCENT_TEXT/ACCENT_SOFT_HOVER, DANGER/DANGER_SOFT_HOVER, INK/ROW, INK/SELECT, MUTED/ROW.
2. Non-CTk surfaces. The mechanism exists since WP3/WP4 and is only exercised here: `ui_theme` registers one `ctk.AppearanceModeTracker.add(handler, root)` at the first `apply_ttk_styles(root)`; the handler re-runs the ttk styles (colours through `ui_theme.resolve`), re-applies stripe and empty-hint colours of every live table and calls the `ui_theme.on_appearance` callbacks, among them `LogUI.refresh_log_colors` (WP4 §G). Verify each of them in dark mode and fix what does not recolour; search the UI modules for other plain-Tk colour uses (`tk.Menu`, canvas items, the link-box placeholder) and route them through `resolve` + `on_appearance`. `SmoothProgressBar._set_appearance_mode` (WP3) must recolour correctly - verify. Icons are `CTkImage`s with light and dark images already; check the sidebar icons, which are the same in both modes.
3. Hard-coded light assumptions. Search all UI modules for colour values that are not `ui_theme` tokens (there must be none after WP5) and for single-colour strings passed where a token tuple is needed (`'white'`, `'transparent'` is fine). Fix only by replacing with tokens in the files this WP owns; anything found in files it does not own is reported to the lead instead.
4. Setting. `ui_settings.py`, card `提醒与界面`: a `setting_row` `外观` / `深色模式适合夜间使用；“跟随系统”会随 Windows 设置切换。` with a `CTkSegmentedButton(values=['浅色', '深色', '跟随系统'])` mapped to `light | dark | system`, stored in `prefs['appearance']`, applied immediately with `ctk.set_appearance_mode(...)` and saved through the normal debounce. `app.py`: on the GUI path (not smoke mode) set `arguments.appearance = settings.load()['appearance']` before constructing `StudioApp`; `StudioApp.__init__` already applies `getattr(arguments, 'appearance', None) or 'light'` (WP4 §A), so `studio.py` is not edited here; default and smoke mode stay `light`. Tests and `snapshot_ui` keep forcing `light` unless they test dark mode. Note for the manual addendum: native dialogs, message boxes, file pickers and right-click menus stay light; `system` makes customtkinter poll the Windows setting.
5. Snapshot. `snapshot_ui.run(..., appearance='dark')`: sets the mode before building the app, repeats all assertions, and adds: no widget below any page returns a light surface (`#FFFFFF`, `#F4F7FC`, `#F7F9FD`) from `cget('fg_color')` when resolved for dark mode (WHITE text tokens excluded); the Treeview style background equals the dark SURFACE; the progress bar canvas background equals the dark SURFACE. Save dark PNGs next to the light ones (`-dark` suffix).
6. Tests. `test_theme.py`: dark contrast for all `TEXT_PAIRS`; switching the mode at runtime recolours a table, a chip, a disabled button and the progress bar without errors; `on_appearance` callbacks fire once per change; the test restores `light` at the end. `test_ui_state.py` is not owned here; run it unchanged.

## Acceptance (verifier)
1. `run_tests.py` exits 0 in the default (light) configuration; every earlier acceptance item of WP3-WP6 still holds.
2. `snapshot_ui.py --out <tmp>` passes all assertions in both modes; in the dark PNGs no white or near-white rectangle remains (tables, log box, link box, progress track, tab bar, empty states), text is readable in every state chip, disabled buttons are distinguishable from enabled ones.
3. Switching 浅色 -> 深色 -> 跟随系统 -> 浅色 in the running app needs no restart and leaves no half-recoloured table or log; the choice survives a restart; with `appearance` absent or invalid the app starts light.
4. A fresh `settings.json` written by 1.5.1 (no `appearance` key) starts light.
5. If this WP is abandoned: restore its owned files from `docs\1.6.0\handoff\snapshot-WP6`; the diff of those files against that folder is then empty, and `run_tests.py` is green.

## Handoff note must include
Final dark token values with measured contrasts, the list of surfaces that stay light by design, screenshots location, whether the package was shipped or dropped (with the reason), and the snapshot folder with the sha256 list (SPEC §7).
